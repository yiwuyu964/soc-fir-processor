## 2. 定点格式

### 2.1 全链路 Q 格式表

| 信号 | 位宽 | Q 格式 | 表示范围（实数） | 说明 |
|---|---|---|---|---|
| `din` 输入样本 x[n] | 16 | Q1.15 | [-1, +0.99997] | 整数域 [-32768, 32767] |
| `h[k]` 系数 | 16 | Q1.15 | [-1, +0.99997] | 整数域 [-32768, 32767] |
| `p[k] = x·h` 乘积 | 32 | Q2.30 | (-1, +1) | 整数域 [-2^30, +2^30] |
| `sum` 累加器 | 40 | Q9.30 | ±512 | 1 符号 + 9 整数 + 30 小数 |
| `dout` 输出 y[n] | 16 | Q1.15 | [-1, +0.99997] | `sum >>> 15` 后饱和 |

定点约定（**RTL 与黄金模型必须完全一致**）：

```
真实值 = 整数值 / 2^15
乘积真实值 = (X · H) / 2^30
输出真实值 = (Σ X·H) / 2^30 / 2^15 = (Σ X·H) >> 15 / 2^15
```

### 2.2 为什么是 Q1.15

- 16 bit 有符号的天然小数格式，1 bit 符号 + 15 bit 小数，全链路统一，不需要任何格式转换逻辑；
- 1 LSB = 2^-15 = 3.05e-5，即满量程的 **0.00305%**，量化噪声底已经远优于赛题 0.1% 的要求；
- 与 `gen_fir_vectors.py` 现有的 `quantize()`、`golden_fir()` 完全一致，**不需要改动黄金模型**。

### 2.3 系数为什么用 16 bit 而不是更宽

赛题只要求「≥16bit」。更宽的系数（如 18/20 bit）能改善阻带衰减，但代价是：

- 每个乘法器从 16×16 变成 18×16 或 20×16，在多数 FPGA 上仍能塞进一个 DSP 单元（DSP48 为 25×18），所以 **DSP 数量不变**；
- 但乘积位宽和累加器位宽都要相应加宽，加法树面积变大；
- 收益（阻带衰减再降几 dB）对本赛题的评分点（功能 + 误差 <0.1%）**没有贡献**。

**结论：取 16 bit。** 若后续综合发现 DSP 有余量、且想冲决赛「资源利用率」之外的滤波性能指标，再考虑加宽，届时需同步改本文 §3 的位宽推导。

## 3. 位宽推导（防溢出的核心）

这一节是任务 5 要求「算出累加位宽防止溢出」的正文。所有数字可用 `fir_fixedpoint_analysis.py` 复算。

### 3.1 乘积位宽：32 bit 足够，且精确

两个 16 bit 有符号数相乘，结果范围：

```
最负: (-32768) × 32767   = -1,073,709,056
最正: (-32768) × (-32768) = +1,073,741,824 = 2^30
```

32 bit 有符号范围是 ±2^31-1 = ±2,147,483,647，**完全容纳**，且没有任何截断。
Verilog 中 `wire signed [31:0] p = x * h;` 自动得到 32 bit 有符号结果，无需手动扩位。

> 现有代码 `fir_cfg.v`：`wire signed [DW+CW-1:0] p [0:NTAP-1];` → 32 bit ✔

### 3.2 累加器位宽：必须按「任意系数」设计

**关键前提**：赛题要求系数**可配置**，CPU 在运行时可以写入任意 16 bit 值。
因此累加器位宽必须按**系数全摆幅**的最坏情况设计，而不能按「当前这一组系数」设计。

最坏情况构造：`x[n] ≡ -32768`（|x| 最大）且 `h[k] ≡ -32768`（|h| 最大），则每个乘积都是 +2^30：

```
|acc|_max = 81 × 2^30 = 86,973,087,744

2^36 = 68,719,476,736
2^37 = 137,438,953,472      ← 上界落在 2^36 与 2^37 之间

log2(86,973,087,744) = 36.340 bit  →  量值需 37 bit  →  有符号需 38 bit
```

> **结论：AW ≥ 38 bit。** 任何小于 38 bit 的累加器，都存在一组合法可配系数使其溢出。

### 3.3 本设计实测界：32 bit（但不作为设计依据）

用仓库里真实的 81 个系数（`fir_soc/08_soc/coeffs.vh`）复算：

| 指标 | 数值 |
|---|---|
| Σ h[k]（直流增益，1.0 = 32768） | **32,772**（偏差 +0.0122%） |
| Σ |h[k]| | **58,500**（= 1.7853 × 32768） |
| 系数范围 | -1624 … +7872，其中 38 个负系数 |
| 对称性 h[k] == h[80-k] | **成立**（线性相位） |
| 最坏 |acc| = 2^15 × Σ|h| | **1,916,928,000** = 2^30.836 |

```
1,916,928,000 < 2^31 = 2,147,483,648
```

**这组系数只需要 32 bit 有符号**——但只有 12% 余量，而且**只要评委/队友改写一次系数，这个结论立刻失效**。
所以本文明确：**32 bit 不作为设计依据**。

### 3.4 为什么最终取 40 bit

| 方案 | 位宽 | 判定 |
|---|---|---|
| 理论下限 | 38 | 刚好不溢出，0 余量 |
| 本组系数下限 | 32 | ❌ 不满足任意系数 |
| **本设计取值** | **40** | ✅ 余量 2 bit，可容忍 4 倍理论最坏值 |

40 bit 的额外代价只有加法树每条路径多 2 bit 宽（约 5% 面积），
换来的是「**无论写入什么系数都不会溢出**」这个可以写进报告、经得起评委追问的硬结论。

> 现有代码 `fir_cfg.v` 的注释写的是「81 阶必须 >= 39，取 40」，方向是对的；
> 本文给出精确值：**下限 38，取 40**。

### 3.5 如果只用 32 bit 会怎样（反例）

沿用 §3.2 的最坏激励，32 bit 累加器会发生回绕：

```
真实 acc = 86,973,087,744
        = 20 × 2^32 + 2^30
32 bit 回绕后 = 2^30 = 1,073,741,824      ← 与真实值相差 81 倍
```

本例中回绕结果右移后仍会被饱和到 +32767，**表面上"看起来正常"**，
但中间量已经错了——这正是溢出最危险的地方：它不一定表现为明显的错误输出。

**因此验证必须直接探针 `sum`，而不是看饱和后的 `dout`。** 见 §8.2。

### 3.6 对称折叠后的位宽（决赛结构）

对称型把 `x[k]` 与 `x[80-k]` 先相加再乘：

| 信号 | 位宽 | 推导 |
|---|---|---|
| `s[k] = x[k] + x[80-k]` | **17** | 两个 Q1.15 相加，范围 [-65536, +65534]，需 17 bit |
| `p_sym = s[k] · h[k]` | **33** | 17 × 16 有符号，上界 ±2^31，需 33 bit |
| 累加 41 项 | **40** | 见下 |

最坏界（任意系数）：

```
|acc| ≤ 2^16 × Σ|h[0..39]| + 2^15 × |h[40]|
       = 2^16 × (40 × 2^15) + 2^15 × 2^15
       = 40 × 2^31 + 2^30
       = 85,899,345,920 + 1,073,741,824
       = 86,973,087,744        ← 与直接型完全相同
```

**对称折叠不改变累加器位宽需求，40 bit 依然成立。** 这是很重要的一点：
优化面积的同时没有引入新的溢出风险。

更漂亮的结论：**两者恒等**。因为系数对称时 Σ|h| = 2·Σ|h[0..39]| + |h[40]|，所以

```
直接型  : 2^15 × Σ|h|
对称折叠: 2^16 × Σ|h[0..39]| + 2^15 × |h[40]|
        = 2^15 × (2·Σ|h[0..39]| + |h[40]|)
        = 2^15 × Σ|h|                        ← 与直接型逐位相同
```

本组系数验证：2^16 × 25,314 + 2^15 × 7872 = **1,916,928,000**，与直接型完全相等。
**对称折叠把乘法器砍掉一半，累加器上界一分钱都没多花。**

### 3.7 输出截位与饱和：位选

40 bit 累加器 `sum` 的位分配：

```
sum[39]        符号位
sum[38:31]     整数部分（溢出检测区）
sum[30:15]     有效输出（右移 15 位后的 Q1.15）
sum[14:0]      被丢弃的小数（截位误差来源）
```

对应现有代码：

```verilog
localparam SHIFT = CW - 1;                              // = 15

wire signed [DW-1:0] y_trunc = sum[SHIFT+DW-1 : SHIFT]; // sum[30:15]
wire overflow = (sum[AW-1 : SHIFT+DW] != {{(AW-SHIFT-DW){sum[SHIFT+DW-1]}}});
                        // 即 sum[39:31] 是否全等于 sum[30] 的符号扩展
wire signed [DW-1:0] y_sat = overflow
                           ? (sum[AW-1] ? 16'sh8000 : 16'sh7FFF)   // 负饱和 / 正饱和
                           : y_trunc;
```

**饱和是必须的**：不饱和直接截断会把大幅值信号回绕成反号，这是 FIR 加速器最常见的功能性 bug。

## 4. 输出量化策略：截位 vs 舍入

### 4.1 位级实现差异

| 方案 | Verilog | 最大误差 | 直流偏置 |
|---|---|---|---|
| **截位（当前）** | `y = sum[30:15]` | 1 LSB = 0.00305% FS | **-0.5 LSB**（向下取整引入） |
| 舍入 | `y = (sum + 2^14) >> 15` | 0.5 LSB = 0.00153% FS | ≈ 0 |

### 4.2 误差预算（最坏叠加）

| 误差源 | 最大误差（占满量程） | 说明 |
|---|---|---|
| 系数量化（Q1.15） | 0.0015% | 单系数 ±0.5 LSB |
| 系数和偏差（直流增益） | **0.0122%** | 实测 Σh = 32,772 vs 理想 32,768 |
| 乘积 / 累加 | **0** | 32 bit 乘积 + 40 bit 累加，全程精确 |
| 输出截位 | 0.0031% | 1 LSB |
| **合计（最坏叠加）** | **0.0168%** | **要求 <0.1%，余量 6.0 倍** |

> 这张表由 `fir_fixedpoint_analysis.py` 自动生成，改一次系数就重算一次。

### 4.3 选型结论

**初赛基线：保持「截位 + 饱和」。**

理由：

1. 误差 0.0168% 已满足 0.1% 要求，余量 6 倍，**没有必要为 0.0015% 的收益冒回归风险**；
2. 现有 `gen_fir_vectors.py` 的黄金模型用的就是截位（`acc >> shift`，Python 对负数向下取整，
   与 Verilog 算术右移语义一致），**RTL 与模型逐位一致，误差为 0**；
3. 改动舍入必须 **RTL 与黄金模型同步改**，否则逐位比对立刻失败——这是一处典型的「改了 A 忘了 B」。

**决赛可选优化：舍入。** 收益是消除 -0.5 LSB 直流偏置、最大误差减半。
若采用，改动清单：

| 文件 | 改动 |
|---|---|
| `fir_soc/rtl/fir_cfg.v` | `sum[30:15]` → `(sum + 40'sd16384)[30:15]`（注意加法要扩位，防自身溢出） |
| `fir_soc/gen_fir_vectors.py` | `y = acc >> shift` → `y = (acc + (1 << (shift-1))) >> shift` |
| 所有 `exp.hex` / `expected.txt` | 用新规则重新生成 |

## 5. 结构选型

### 5.1 三种候选结构对比

| 维度 | 直接型（Direct Form，全并行） | 转置型（Transposed Form） | 对称型（Symmetric / 折叠） |
|---|---|---|---|
| 差分方程 | y[n] = Σ h[k]·x[n-k] | y[n] = h[0]x[n] + z1[n-1]，逐级级联 | y[n] = Σ_{k=0}^{39} h[k]·(x[k]+x[80-k]) + h[40]·x[40] |
| 乘法器数量 | 81 | 81 | **41** |
| 关键路径（未流水） | 乘法器 + 加法树 | **1 乘法器 + 1 加法器** | 预加 + 乘法器 + 加法树 |
| 寄存器开销 | 延迟线 81×16 | 延迟线 + **81 个累加宽度寄存器** | 延迟线 + 40×17 预加寄存器 |
| 对称优化 | 容易（在延迟线抽头上预加） | 较难（无共享抽头） | **原生支持** |
| 吞吐 | 1 sample/cycle | 1 sample/cycle | 1 sample/cycle |
| 对本赛题的适配 | 改动最小，与现有回归完全兼容 | 时序最好但寄存器开销大、不利于对称优化 | DSP 减半，决赛「架构创新」明示加分项 |

### 5.2 关键路径分析

未流水的直接型关键路径 = 1 级乘法器 + 加法树深度 + 截位/饱和。

- 乘法器：16×16 有符号，若推断为 DSP 单元约 3–5 ns；若退化为 LUT 乘法约 6–10 ns；
- 加法树 81→41→21→11→6→3→2→1，深度 **7 级**，每级 40 bit 加法约 0.8–1.5 ns → 6–10 ns；
- 截位 + 比较 + 饱和：约 1–2 ns。

合计约 10–22 ns，对应 Fmax 约 45–100 MHz——**在 50 MHz 附近，没有余量**。

**转置型**的关键路径只有「1 乘法器 + 1 加法器」，约 4–6 ns，Fmax 很高；
但它需要 81 个 40 bit 寄存器（3,240 FF）常驻，且对称折叠无法直接套用，
对本赛题「资源利用率 20 分」不利，**不选**。

### 5.3 选型结论：两阶段走

| 阶段 | 结构 | 乘法器 | 目标 |
|---|---|---|---|
| **初赛（10.19）** | 直接型全并行 + **流水线加法树** | 81 | 功能正确 + 时序收敛 + 与现有 TB 回归兼容 |
| **决赛** | 对称型折叠 + 流水线加法树 | **41** | 资源减半，冲「架构创新 20 分」 |

这样分阶段的原因：初赛评分只看功能正确性与协议合规，**不看资源**；
而对称折叠要动系数寄存器语义（见 §5.4），属于有回归风险的结构性改动，
放在初赛交付之后做，风险和时间都可控。

### 5.4 对称折叠的一个必须提前定的接口问题

对称折叠意味着硬件内部用 `h[0..40]` **镜像**出另外 40 个系数。
若 CPU 写入的系数不满足 h[k]==h[80-k]，结果就是错的。两种处理：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 系数寄存器收缩为 41 项，`COEF[0..40]`，硬件镜像；AXI 地址映射相应缩小 | 驱动 `fir_regs.h` 与 TB 需同步改 |
| B | 保留 81 项系数寄存器，增加 `SYM_EN` 配置位；`SYM_EN=0` 时走通用路径 | 通用路径仍需 81 乘法器 → **面积省不下来，方案失效** |

**结论：若做对称优化，只能走方案 A**，并在技术报告中明确写「本设计约定线性相位对称系数，
是赛题『自行设计系数』范围内的架构选择」。
**这件事必须在动 RTL 之前决定**，否则会连带改动驱动、地址映射表和整套 TB。

## 6. 流水线方案

### 6.1 现状：为什么必须流水

现有 `fir_cfg.v` 的累加是**串行链**，不是加法树：

```verilog
always @(*) begin
    sum = 0;
    for (k = 0; k < NTAP; k = k + 1)
        sum = sum + {{...}, p[k]};      // ← 81 级依次串起来
end
```

综合后这是一条 **81 级 40 bit 串行加法链**，估算 32–65 ns，
对应 Fmax 约 **15–31 MHz**——**25 MHz 已无余量，50 MHz 必然不收敛**。

这不是「优化」，是**上板的硬前提**。

### 6.2 加法树：把 81 项串行改成 7 级树

```
第 1 级: 81 → 41   （40 个加法器 + 1 项直通）
第 2 级: 41 → 21
第 3 级: 21 → 11
第 4 级: 11 → 6
第 5 级: 6  → 3
第 6 级: 3  → 2
第 7 级: 2  → 1
```

深度从 **81 级降到 7 级**，同样 80 个加法器，面积几乎不变，速度提升一个数量级。

**位宽策略**：各级节点最多容纳 2^L 个乘积，理论上第 L 级只需 32+L bit。
实现上建议**全部统一用 40 bit**（实现和验证都简单），
若决赛面积吃紧，再按 `32 + L` 逐级收窄。

### 6.3 打拍方案：初赛基线 5 级流水

| 流水级 | 组合逻辑 | 打拍内容 |
|---|---|---|
| — | 延迟线移位（天然 1 拍） | x[0..80] |
| **S1** | 81 个 16×16 有符号乘法 | p[0..80]，32 bit × 81 |
| **S2** | 加法树 第 1–3 级 | 40 bit × 11 |
| **S3** | 加法树 第 4–5 级 | 40 bit × 3 |
| **S4** | 加法树 第 6–7 级 | 40 bit × 1 |
| **S5** | 右移 15 位 + 溢出判断 + 饱和 | dout，16 bit |

**总流水深度 LAT = 5 拍，吞吐恒为 1 sample/cycle。**

### 6.4 对称版：决赛 6 级流水

| 流水级 | 组合逻辑 |
|---|---|
| **S0** | 40 个 17 bit 预加：s[k] = x[k] + x[80-k] |
| **S1** | 41 个 17×16 乘法 → 33 bit |
| **S2** | 加法树 第 1–2 级（41→21→11） |
| **S3** | 加法树 第 3–4 级 |
| **S4** | 加法树 第 5–6 级 |
| **S5** | 右移 + 饱和 |

**LAT = 6 拍，吞吐仍为 1 sample/cycle。**

### 6.5 时序预算（目标 50 MHz，周期 20 ns）

| 流水段 | 估算延迟 | 是否满足 20 ns |
|---|---|---|
| S1 乘法段（DSP 推断） | 3–5 ns | ✅ 余量 4 倍 |
| S1 乘法段（LUT 退化时） | 6–10 ns | ✅ 余量 2 倍 |
| S2/S3/S4 加法段（每段 2–3 级） | 2–4.5 ns | ✅ |
| S5 截位/饱和段 | 1–2 ns | ✅ |

即便乘法器退化为 LUT 实现，最长段也只有 10 ns 左右，
**50 MHz 有 2 倍余量，100 MHz 仍有余地**。

### 6.6 吞吐与延迟的取舍

流水线**不降低吞吐**（仍为 1 sample/cycle），只增加固定延迟：

```
系统总延迟 ≈ LAT × Tclk = 5 × 20 ns = 100 ns @50MHz
```

相对决赛指标「系统总延迟（μs 级）」，100 ns 由 FIR 贡献的部分可以忽略。
**用 100 ns 的延迟换一个数量级的频率余量，是明显划算的。**

## 7. 对现有代码的影响

### 7.1 端口不变

流水线**不改变 `fir_cfg.v` 的任何端口**（`en / din / dout / dout_v / flush / coef_*`），
因此 `fir_axi.v`、`soc_top.v`、`soc_cm0_top.v` **无需改动**。

### 7.2 `dout_v` 必须与数据同步延迟

这是流水线改造最容易出错的地方：**数据延了几拍，`dout_v` 就要延几拍**。
建议实现为一个与数据流水线等长的移位寄存器：

```verilog
reg [LAT-1:0] v_pipe;
always @(posedge clk or negedge rst_n)
    if (!rst_n) v_pipe <= 0;
    else        v_pipe <= {v_pipe[LAT-2:0], en};
assign dout_v = v_pipe[LAT-1];
```

若 `dout_v` 忘了延迟，FIFO 会写入未就绪的数据，现象是「结果整体错位几拍」——
容易被误判成算法错误，实际是握手信号没对齐。

### 7.3 TB 里的 `got[i+1]` 偏移要不要改？

现有 TB（`05_fir81/tb_fir.v`、`08_soc/tb_soc.v`）都用固定偏移：
「DUT 比黄金模型多 1 拍流水线前导，`got[0]` 恒为 0，从 `got[1]` 开始比」。

**分析结论：只要 `dout_v` 与数据同步延迟，输出序列本身不变，只是整体时间平移。**

理由：流水线各级之间每拍都在推进，输入样本仍然每拍进入一个，
因此第 i 个「被 `dout_v` 标记为有效」的输出，仍然是序列中的第 i 个结果。
第 1 个被标记的输出依然是「延迟线全零时的结果 = 0」。

**所以 `got[i+1]` 的约定可以保持不变。** 但这是一个推理结论，**必须实测确认**：

- [ ] 改完流水线后，重跑 `05_fir81` 回归，确认 `PASS: 336 个样本逐位一致`；
- [ ] 若失败且错位固定为 k 拍，说明 `dout_v` 与数据的延迟拍数不一致，回头查 §7.2，**不要改 TB 去迁就**。

| `fir_soc/rtl/fir_cfg.v` | **要改** | 串行累加链 → 流水线加法树（唯一的必改项） |

## 8. 验证计划

本文提出的每个位宽结论，都要有对应的验证用例。四项与 FIR 定点直接相关：

### 8.1 逐位一致回归（已有，保持）

```
.\sim.bat 05_fir81        → PASS: 336 个样本与黄金模型逐位一致
python gen_fir_vectors.py --check 05_fir81\got.hex
```

流水线改造后必须重新跑通，这是**不能退化的底线**。

### 8.2 累加器不溢出专项（**新增，证明 40 bit 的必要性**）

| 用例 | 激励 | 系数 | 检查点 |
|---|---|---|---|
| OV-1 最坏正溢出 | x[n] ≡ -32768 | h[k] ≡ -32768 | 直接探针 `dut.sum`，应等于 86,973,087,744，不得回绕 |
| OV-2 最坏负溢出 | x[n] ≡ -32768 | h[k] ≡ +32767 | `sum` = -86,941,319,168，应在 40 bit 范围内 |
| OV-3 边界饱和 | x[n] ≡ 32767 | h[0]=32767，其余 0 | 输出应为 +32767（正饱和），不得回绕成负数 |
| OV-4 负饱和 | x[n] ≡ -32768 | h[0]=32768（即 -32768） | 输出应为 -32768（负饱和） |

**关键**：OV-1/OV-2 必须探针 `sum`（用 `dut.sum` 层次引用或加调试端口），
因为如 §3.5 所示，回绕后的值经饱和后**可能看不出异常**。

> 这组用例同时也是给评委看的证据：「我们不是随便定了个 40 bit，而是有反例、有验证。」

### 8.3 对称性专项（决赛做对称折叠时）

- 逐位比对 `h[k]` 与 `h[80-k]` 在硬件内部是否一致镜像；
- 用一组**故意不对称**的系数喂进去，确认结果与直接型一致（若走方案 A，则应明确记录「不对称系数属于约定外输入」）。

### 8.4 误差 vs 浮点参考（赛题 6.1 的 <0.1%）

现有做法是「与定点黄金模型逐位一致」，比 0.1% 严格得多。
建议**再加一层**：用浮点（Python 纯浮点 `convolve`）算一遍，给出实测最大相对误差，
把 §4.2 的 0.0168% 预算表用实测数据证实。报告里这张表很有说服力。
