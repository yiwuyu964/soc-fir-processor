## 一、结论速览

| 项 | 取值 | 依据 |
|---|---|---|
| 数据定点格式 | Q1.15，16 bit 有符号 | 赛题要求数据宽度 16bit |
| 系数定点格式 | Q1.15，16 bit 有符号 | 赛题要求 ≥16bit，16 位是资源最优解 |
| 乘积位宽 | 32 bit（Q2.30） | 16×16 有符号乘积精确落在 32 bit 内，无截断 |
| 累加器位宽 | 40 bit（理论上限 38） | 任意可配系数的最坏界 2^36.36 |
| 输出处理 | 算术右移 15 位 + 饱和到 16 bit | 回到 Q1.15，防回绕 |
| 结构（初赛） | 直接型全并行，82 乘法器 + 流水线加法树 | 改动最小，与回归兼容，时序可收敛 |
| 结构（决赛） | 对称型折叠，41 乘法器 + 预加法器 | 决赛「架构创新」明示加分项 |
| 流水线 | 5 级，吞吐恒为 1 sample/cycle | 延迟 100 ns @50MHz |
| 误差 | 与定点黄金模型逐位一致；浮点 RRMSE < 0.1% | 实测，见第七节 |

## 三、定点格式

### 3.1 全链路 Q 格式

| 信号 | 位宽 | Q 格式 | 表示范围 | 整数域 |
|---|---|---|---|---|
| 输入样本 `din` | 16 | Q1.15 | [-1, +0.99997] | [-32768, 32767] |
| 系数 `h[k]` | 16 | Q1.15 | [-1, +0.99997] | [-32768, 32767] |
| 乘积 `p[k]` | 32 | Q2.30 | (-1, +1) | ±2^30 |
| 累加 `sum` | 40 | Q9.30 | ±512 | 1 符号 + 9 整数 + 30 小数 |
| 输出 `dout` | 16 | Q1.15 | [-1, +0.99997] | `sum >>> 15` 后饱和 |

换算关系在 RTL 和黄金模型里必须完全一致：

```
真实值       = 整数值 / 2^15
乘积真实值    = (X · H) / 2^30
输出真实值    = (Σ X·H) / 2^30 / 2^15
```

### 3.2 为什么用 Q1.15

16 位有符号的天然小数格式，1 位符号加 15 位小数，全链路统一，中间不需要任何格式转换逻辑。1 个 LSB 等于 2^-15 ≈ 3.05e-5，也就是满量程的 0.00305%——量化噪声本底已经比赛题要求的 0.1% 低两个量级。

选它还有一个现实原因：黄金模型脚本（`fir/fir_coeff.py`）里的 `quantize()` 和卷积就是按 Q1.15 写的，RTL 跟着它走，两边的截位和舍入规则天然对齐。

### 3.3 系数为什么不加宽

赛题只要求"≥16bit"。加到 18 位或 20 位确实能让阻带再深几 dB，代价是乘积位宽和累加器位宽都要跟着加宽，加法树面积变大；而且在多数 FPGA 上 18×16 依然塞得进一个 DSP48（25×18），DSP 数量不会减少，等于白付面积换一点对本赛题评分没有贡献的指标。

结论是 16 位。如果将来综合发现 DSP 还有富余，且想冲决赛的滤波性能指标，再考虑加宽，那时候本文第三节的位宽推导要同步改。

## 四、位宽推导

这一节是任务 5 要求的"算出累加位宽防止溢出"的正文。

### 4.1 乘积：32 位足够且精确

两个 16 位有符号数相乘，极值出现在两个负数相乘：

```
最负：(−32768) × 32767   = −1,073,709,056
最正：(−32768) × (−32768) = +1,073,741,824 = 2^30
```

32 位有符号的范围是 ±(2^31−1) ≈ ±2.15e9，完全容得下，而且**没有任何截断**——乘积是精确的。Verilog 里 `wire signed [31:0] p = x * h;` 会自动得到这个位宽，不用手动扩位。

### 4.2 累加器：必须按"任意系数"设计

这里有个前提容易被忽略：赛题要求系数可配置，CPU 运行时可写入任意 16 位值。所以累加器位宽必须按系数全摆幅的最坏情况定，不能按"当前这组系数"定。

最坏情况是把输入和系数都推到负满幅：`x[n] ≡ −32768` 且 `h[k] ≡ −32768`，此时每个乘积都是 +2^30，82 个加起来：

```
|acc|_max = 82 × 2^30 = 88,046,829,568

2^36 = 68,719,476,736
2^37 = 137,438,953,472       ← 上界落在两者之间

log2(88,046,829,568) = 36.358 bit
→ 量值需 37 位，有符号需 38 位
```

结论很清楚：**累加器至少 38 位**。任何小于 38 位的设计，都存在一组合法可配系数让它溢出。

### 4.3 只看当前这组系数会得出错误结论

如果只按 `fir/coeffs.vh` 里现存的那组系数算，最坏累加值约 2^30.8，32 位就够用了。这个结论本身没错，但它有 12% 的余量，而且**只要有人改写一次系数就立刻失效**。

所以本文明确：32 位不作为设计依据。设计取值 40 位，比理论下限多 2 位。代价是加法树每条路径宽 2 位，面积大约多 5%；换来的是"无论写入什么系数都不会溢出"这个能经得起评委追问的结论。

### 4.4 如果只用 32 位会怎样

沿用 §4.2 的激励，32 位累加器会回绕：

```
真实 acc = 88,046,829,568 = 20 × 2^32 + 2^30
32 位回绕后 = 2^30 = 1,073,741,824      ← 与真实值差 82 倍
```

本例中回绕结果右移后仍会被饱和到 +32767，表面上"看起来正常"，但中间量早就错了。这正是溢出最危险的地方——它不一定表现为明显的错误输出。

所以验证必须直接探针 `sum`，而不是只看饱和后的 `dout`。具体做法见第七节。

### 4.5 对称折叠不改变位宽需求

决赛想做的对称折叠，把 `x[k]` 和 `x[81−k]` 先相加再乘。直觉上会以为位宽需求变了，实际算一遍：

```
|acc| ≤ 2^16 × Σ|h[0..40]|
      = 2^16 × (41 × 2^15)
      = 41 × 2^31
      = 88,046,829,568        ← 与直接型完全相同
```

为什么恒等？因为系数对称时 Σ|h| = 2·Σ|h[0..40]|，所以

```
直接型  : 2^15 × Σ|h|            = 2^15 × 2 × 41 × 2^15 = 41 × 2^31
对称折叠: 2^16 × Σ|h[0..40]|     = 2^16 × 41 × 2^15     = 41 × 2^31
```

两边逐位相同。也就是说，对称折叠把乘法器从 82 个砍到 41 个，累加器上界一分钱没多花，也没有引入新的溢出风险。

### 4.6 输出截位与饱和

40 位累加器的位分配：

```
sum[39]      符号位
sum[38:31]   整数部分（溢出检测区）
sum[30:15]   有效输出（右移 15 位后的 Q1.15）
sum[14:0]    被丢弃的小数（截位误差来源）
```

对应到的代码是 `RTL/fir_core.v` 里的这一段：

```verilog
localparam SHIFT = CW - 1;                               // = 15
wire signed [DW-1:0] y_trunc = sum[SHIFT+DW-1 : SHIFT];   // sum[30:15]
wire overflow = (sum[AW-1 : SHIFT+DW] != {{(AW-SHIFT-DW){sum[SHIFT+DW-1]}}});
wire signed [DW-1:0] y_sat = overflow
                           ? (sum[AW-1] ? 16'sh8000 : 16'sh7FFF)
                           : y_trunc;
```

饱和是必须做的，不能省。不饱和直接截断会把大幅值信号回绕成反号，这是 FIR 加速器最常见的一类功能性 bug，排查时又很容易误判成算法问题。

## 五、结构与流水线

### 5.1 三种候选结构

| 维度 | 直接型（全并行） | 转置型 | 对称型（折叠） |
|---|---|---|---|
| 乘法器数量 | 82 | 82 | 41 |
| 关键路径（未流水） | 乘法器 + 加法树 | 1 乘 + 1 加 | 预加 + 乘法器 + 加法树 |
| 寄存器开销 | 延迟线 82×16 | 延迟线 + 82 个累加宽度寄存器 | 延迟线 + 41×17 预加寄存器 |
| 对称优化 | 容易 | 较难 | 原生支持 |
| 吞吐 | 1 sample/cycle | 1 sample/cycle | 1 sample/cycle |
| 适配性 | 改动最小，与回归兼容 | 时序好但寄存器开销大 | DSP 减半，决赛加分项 |

转置型的关键路径只有"1 乘法 + 1 加法"，约 4–6 ns，Fmax 很高；但它需要 82 个 40 位寄存器常驻（三千多个 FF），而且对称折叠套不上去，对"资源利用率 20 分"不利，所以没选。

### 5.2 为什么必须是加法树而不是串行链

最初的实现是串行累加：

```verilog
always @(*) begin
    sum = 0;
    for (k = 0; k < NTAP; k = k + 1)
        sum = sum + {{...}, p[k]};   // 82 级依次串起来
end
```

综合出来是一条 82 级 40 位串行加法链，估算延迟 32–65 ns，对应 Fmax 只有 15–31 MHz。25 MHz 的下限都已经擦边，50 MHz 必然不收敛。

换成加法树后深度从 82 级降到 7 级：

```
第 1 级: 82 → 41
第 2 级: 41 → 21
第 3 级: 21 → 11
第 4 级: 11 → 6
第 5 级: 6  → 3
第 6 级: 3  → 2
第 7 级: 2  → 1
```

加法器总数还是 81 个（n 个输入做二叉树正好用 n−1 个加法器），面积几乎不变，但关键路径从 81 级降到 7 级，速度提升一个数量级。所以这不是"优化"，而是上板的硬前提。

### 5.3 五级流水（已实现）

| 流水级 | 组合逻辑 | 打拍内容 |
|---|---|---|
| — | 延迟线移位 | `x[0..81]` |
| S1 | 82 个 16×16 有符号乘法 | `p[0..81]`，32 bit × 82 |
| S2 | 加法树第 1–3 级（82→41→21→11） | 40 bit × 11 |
| S3 | 加法树第 4–5 级（11→6→3） | 40 bit × 3 |
| S4 | 加法树第 6–7 级（3→2→1） | 40 bit × 1 |
| S5 | 右移 15 位 + 溢出判断 + 饱和 | `dout`，16 bit |

`LAT = 5`，吞吐恒为 1 sample/cycle。

### 5.4 吞吐与延迟的取舍

流水线不降低吞吐，只增加固定延迟：

```
系统总延迟中 FIR 贡献 = LAT × Tclk = 5 × 20 ns = 100 ns @ 50MHz
```

决赛指标里的"系统总延迟"是微秒量级（要算上 DMA 搬运和 CPU 配置），100 ns 在其中可以忽略。用 100 ns 的延迟换一个数量级的频率余量，这笔账很划算。

### 5.5 决赛的对称折叠，有一个接口问题必须先定

对称折叠意味着硬件内部用 `h[0..40]` 镜像出另外 41 个系数。如果 CPU 写进来的系数不满足 h[k] == h[81−k]，结果就是错的。两种处理方式：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 系数寄存器收缩到 41 项，硬件镜像；AXI 地址映射相应缩小 | 驱动和 TB 需要同步改 |
| B | 保留 82 项寄存器，加 `SYM_EN` 配置位 | 通用路径仍需 82 个乘法器，面积省不下来，方案失效 |

只能走 A。同时要在技术报告里明确写"本设计约定线性相位对称系数，属于赛题『自行设计系数』范围内的架构选择"。这件事必须在动 RTL 之前定，否则会连带改驱动、地址映射表和整套测试台。

## 六、截位还是舍入

| 方案 | 实现 | 最大误差 | 直流偏置 |
|---|---|---|---|
| 截位（当前） | `y = sum[30:15]` | 1 LSB = 0.00305% FS | −0.5 LSB |
| 舍入 | `y = (sum + 2^14) >> 15` | 0.5 LSB = 0.00153% FS | ≈ 0 |

初赛保持截位。理由不是"截位更好"，而是**一致性**：截位规则与冻结契约、定点黄金模型完全一致——`fir/fir_coeff.py` 里用的就是 `acc >> shift`，Python 对负数向下取整，和 Verilog 算术右移语义相同。RTL 与模型逐位一致，误差严格为零。如果改成舍入，RTL 和黄金模型必须同时改，否则逐位比对立刻失败，这是典型的"改了 A 忘了 B"。

决赛可以改舍入，收益是消掉 −0.5 LSB 的直流偏置、最大误差减半。改动清单只有三处：`fir_core.v` 里 `sum[30:15]` 改成 `(sum + 40'sd16384)[30:15]`（注意加法要扩位，否则自己会溢出）、`fir/fir_coeff.py` 的截位规则、以及重新生成全部 `exp.hex`。

## 七、验证

每一条位宽结论都有对应的测试用例，这一节记录做到哪一步了。

### 7.1 逐位一致（已通过）

`tb_fir_core` 比对 337 个样本与黄金模型，逐位一致。这是不能退化的底线，流水线改造后重跑仍然 PASS。

### 7.2 累加器不溢出专项（已通过）

| 用例 | 激励 | 系数 | 检查点 |
|---|---|---|---|
| OV-1 | x ≡ −32768 | h ≡ −32768 | 探针 `sum` = 88,046,829,568，不得回绕 |
| OV-2 | x ≡ −32768 | h ≡ +32767 | `sum` = −88,044,142,592，落在 40 位范围内 |
| OV-3 | x ≡ 32767 | h[0]=32767，其余 0 | 输出 +32767（正饱和） |
| OV-4 | x ≡ −32768 | h[0]=−32768 | 输出 −32768（负饱和） |

前两项必须直接探针 `sum`，因为如 §4.4 所述，回绕后的值经过饱和可能看不出异常。这组用例同时也是给评委看的证据——40 位不是随便定的，有反例也有验证。

### 7.3 浮点参考误差（已通过）

除了与定点模型逐位比，还加了一层：用 Python 纯浮点算一遍卷积，输出实测最大相对误差。`tb_fir` 的结论是 RRMSE < 0.1%，比赛题要求更严。报告里这张实测表比预算估算有说服力得多。

### 7.4 时序收敛（已达成）

`docs/validation-20261018/final_timing.rpt` 记录的是布线后的结果：

| 指标 | 目标 | 实测 |
|---|---|---|
| 时钟约束 | 50 MHz | `create_clock -period 20.000` |
| 建立时间余量 WNS | > 0 | **+0.217 ns** |
| 结论 | 收敛 | All user specified timing constraints are met |

### 7.5 对称折叠专项

决赛做折叠时才需要。检查两项：硬件内部 `h[k]` 与 `h[81−k]` 是否真的镜像；用一组故意不对称的系数喂进去，结果应符合"约定外输入"的定义。
