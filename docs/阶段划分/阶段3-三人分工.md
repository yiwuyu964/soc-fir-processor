## 二、这次和阶段 2 不同：有自定义接口必须冻结

阶段 2 三个人的连接点全是标准 AXI4，规范本身就是契约，不用开会。

DMA 不一样。它在内部切成三块——寄存器组、顶层、引擎——块与块之间走的是自定义信号，必须先把这些信号定死。好在只有两个接口，一次会议能定完，但细节不少：`LEN=0` 是什么含义、`START` 是脉冲还是电平、4KB 拆分责任归谁、错误怎么处理、中断是电平还是脉冲，这类语义一共十五处，全部要三个人确认过才算冻结，清单在 `../契约/契约AB-DMA内部接口.md` §5。

| 契约 | 内容 | 定义位置 |
|---|---|---|
| A | `dma_regs` 到顶层的 cfg 配置总线 | `契约AB-DMA内部接口.md` §1 |
| B | `dma_engine` 的端口（B 实现，A 例化六次） | `契约AB-DMA内部接口.md` §2 |
| C | AXI ID 编码 `{CH[2:0], 1'b1}` | `契约C-AXI ID编码.md` |
| — | 中断分配 IRQ2~7 / IRQ8 | `任务3`、`任务4` 已冻结 |
| — | 寄存器映射（每通道 SRC/DST/LEN/CTRL） | `任务3` 4.2 节 |

中断分配已经冻结，不用再讨论：

| 信号 | 位宽 | 接到 |
|---|---|---|
| `irq_done[5:0]` | 6 | IRQ2~IRQ7，通道 0~5 各一个 |
| `irq_err` | 1 | IRQ8，全局错误；具体哪个通道出错要读 `CTRL[29]` 排查 |

契约拆成独立文档是刻意的：A、B、C 由不同的人维护，拆开后每个人只改自己那份，合并时零冲突。阶段 1 把契约 D 拆出去用的是同样的办法。

## 三、一个重要的简化：三种传输场景不需要三套硬件

阶段目标写了「支持存储器↔FIR、存储器↔存储器、UART↔存储器」，听起来是三种场景，实际在硬件上是同一件事——把数据从 SRC 搬到 DST。差别只在地址要不要递增：

| 场景 | SRC_INC | DST_INC |
|---|---|---|
| 存储器 → 存储器 | 1 | 1 |
| 存储器 → FIR 的 DIN | 1 | 0（DIN 是固定地址，每写一拍喂一个样本） |
| FIR 的 DOUT → 存储器 | 0（轮询读同一地址） | 1 |
| UART → 存储器 | 0（RXDATA 固定地址） | 1 |
| 存储器 → UART | 1 | 0（DATA 固定地址） |

所以引擎只要支持"源和目的各自可选递增"就够了，这正是 `CTRL` 的 bit1 和 bit2 的用途。这个认识省掉了至少两套专门逻辑，也解释了为什么 FIR 和 UART 能被 DMA 当成普通存储器访问——它们的寄存器在地址空间里就是固定地址。

## 四、三人分工

### A —— DMA 配置通路与顶层集成

新建 `RTL/dma_regs.v` 和 `RTL/dma.v`，分支 `phase3-A-dma-top`。

`dma_regs.v` 是 AXI4 从口（5 通道带 ID），基址 `0x4000_1000`，内部有 6 通道 × 4 个寄存器共 24 个。写 `CTRL[0]=1` 产生 `start` 脉冲给对应通道，读 `CTRL`/`STATUS` 回状态。

`dma.v` 顶层负责例化一个 `dma_regs` 加六个 `dma_engine`；做 6→1 的 AXI4 主口仲裁（round-robin、突发期间锁定，和阶段 2 互连同样的思路）；生成 `irq_done[5:0]` 和 `irq_err`；预留链式传输的参数 `CHAIN_EN`（默认 0），本阶段不实现。

验收：24 个寄存器读写正确、单通道搬运跑通、6 通道同时启动时仲裁不饿死任何一路、每通道完成后 `irq_done` 对应位拉高、从口和主口都零违规。

为了避免等 B 的引擎，先用一个空壳 `dma_engine`（端口齐全、只回 `busy=0, done=0`）把顶层和仲裁写通，真引擎到了直接替换。

实际结果：`tb_dma` 69 项、`tb_dma_self` 70 项、`tb_dma_ic` 14 项全过。

### B —— DMA 数据搬运引擎

新建 `RTL/dma_engine.v`，分支 `phase3-B-dma-engine`，接口严格按契约 B。

核心是单通道搬运：从 `cfg_src` 读 `cfg_len` 个字写到 `cfg_dst`。读突发用 INCR 加正确的 RLAST，写突发用 INCR 加正确的 WLAST、`WSTRB` 全 1（整字传输）；单拍 `LEN=0` 只是 INCR 的特例，不用单独写一套。

4KB 边界要自动拆分。`AWLEN`/`ARLEN` 最大 256 拍，而且一个突发不许跨 4KB 边界，所以搬 1000 个字得自动切成若干段。这件事不做的话，长传输会直接违反协议，检查器会报出来。

地址递增由 `cfg_src_inc`/`cfg_dst_inc` 各自控制，对应第三节那张表。

流控上，读回来的数据要能暂存，等写通道有空再发，`RTL/sync_fifo.v` 已经现成可以直接例化。错误处理是 `BRESP`/`RRESP` 为 `SLVERR` 时停传输并拉高 `err`。

验收：单拍搬运正确、INCR 突发正确（含超过 256 拍的长传输自动拆分）、跨 4KB 边界被正确拆分、`SRC_INC=0` 或 `DST_INC=0` 时地址保持不变、错误响应能让引擎停下来、主口零违规。

实际结果：`tb_dma_engine` 21 项全过。

### C —— DMA 验证

新建存储器模型和主测试台，分支 `phase3-C-dma-tb`。

要做的是一个 AXI4 从设备模型（当存储器用，挂 64KB 数组，支持单拍和 INCR 突发、`WSTRB`、RLAST，并能故意注入延迟逼出流控问题），外加 `tb_dma.v` 覆盖这些场景：24 个寄存器逐个写读；存储器到存储器的单拍与 INCR（含跨 4KB 长传输）；`DST_INC=0` 的固定地址搬运并检查地址没变；往固定地址写 N 个样本检查顺序；6 通道并发检查仲裁不饿死；中断用例（每通道完成后 `irq_done[N]` 单独拉高、错误注入后 `irq_err` 拉高、电平或脉冲形状符合 `任务4` 的定义）。

让 C 专门做验证而不写 RTL，是有意的安排——自己测自己的代码容易漏，独立的验证者才挑得出问题。

实际结果：原本计划的 `TB/dma_slave_model.v` 没有单独成文件。后来审计时发现两个测试台各自定义了一份 AXI 从设备模型，单独编译都过，一起编译就报重复声明；于是统一成了公共件 `TB/axi_mem_model.v`，两边共用。这个教训在当时只是当成命名冲突处理，事后看它暴露的是更普遍的问题——重复代码在集成阶段才炸。

## 五、为什么这次也能三个人同时开工

靠空壳，和阶段 1 一样的办法：

| 人 | 依赖谁 | 怎么先开工 |
|---|---|---|
| A | 需要 B 的引擎 | 先写空壳引擎（端口齐全、行为为空），把顶层和仲裁跑通 |
| B | 谁都不依赖 | 引擎对外是标准 AXI4 主口，配一个从设备模型就能单独测 |
| C | 需要接口，不需要实现 | 按契约写 TB，对着空壳也能跑，只是结果不对 |

三个人第一天都能开工。

## 七、集成验收

三条分支合进 main 之后：

```
CPU ──AXI 从口──▶ dma_regs（A）
                      │ cfg
                      ▼
                 dma.v 顶层（A）  ── 6→1 AXI 仲裁 + 中断生成
                      │
              eng0 … eng5（B，每个对外是 AXI4 主口）
                      │ AXI4 主口，ID = {CH, 1'b1}
                      ▼
                阶段 2 的 AXI 互连
```

要测的场景：6 通道各自单独搬运；6 通道同时搬运；存储器到固定地址（模拟 UART/FIR）；固定地址到存储器；六个 `irq_done` 加一个 `irq_err`；主口和从口检查器均零违规；接进互连后 CPU 与 DMA 同时访问不出错。

最后一条后来单独补了一个测试台。原因是 `tb_dma` 把 DMA 直连存储器模型，绕过了互连，地址译码和 ID 回选那条链根本没被验证——`tb_dma_ic` 就是为补这个缺口建的。
