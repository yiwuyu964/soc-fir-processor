## 一、比赛本身

飞腾信息技术有限公司出的题，全称《带高阶 FIR 数字滤波器的 SoC 处理器设计》，属于"中国电子杯"第三届"四邮四电"高校 ICT 产教融合创新大赛的芯片设计与应用赛道。

要做的东西说起来不复杂：一颗 Cortex-M0 在 FPGA 上运行，通过 AXI 总线指挥一个硬件 FIR 滤波器。CPU 负责配置系数、下发任务，FIR 负责算，中间由 DMA 搬数据，结果从串口打印出来。难点不在算法——系数是 Python 算好的——而在总线的正确性和时序收敛。

评分分两轮，策略差别很大。初赛只看功能对不对、文档清不清楚，完全不看性能；决赛才比吞吐量、资源占用和架构创新。所以初赛的唯一目标是把一个功能完整、逐位正确的版本做出来，性能优化留到后面。

## 二、要交什么

| 提交物 | 规格 |
|---|---|
| 技术报告 | DOC + PDF 各一份，≤80 页，一个文档 |
| 源代码包 | 压缩包，含 RTL 源码 + Testbench + C 驱动源码 |
| 汇报 PPT | ≤15 页 |
| 讲解视频 | mp4，8 分钟 |
| 演示视频 | mp4，≤5 分钟，FPGA 实机演示（决赛） |

有两条红线写在赛题原文里，踩了直接出局。一是文档和视频中不能出现队伍单位、指导老师等身份信息；二是计分项不能使用开源代码——FIR、DMA、桥、互连这些 RTL 必须自己写，iverilog、GTKWave、git 这类工具不算。

报告结构也是硬性要求的四段式：工作原理与关键算法、体系结构设计、详细设计与实现、三层验证。三层验证指的是单元/模块验证、不含 CPU 的集成验证、含 CPU 的系统测试。

评分细则里有两句话值得单独拎出来看。"FIR 结果与软件参考值误差 < 0.1%"——我们做到的是逐位一致，误差为零，这一条拿满。"DMA 6 通道全部独立工作、数据零差错"——测试里专门有一项让 6 个通道并发启动，验证仲裁不会饿死任何一个。

决赛另算：性能指标占 40%（FIR 吞吐量、DMA 带宽、CPU 主频、系统总延迟，排名制），资源利用率 20%，架构创新 20%，现场答辩 20%。赛题在"架构创新"里明示了两个方向——FIR 对称系数优化（81 阶压到 41 次乘加）和 DMA 链式传输，评委显然是期待看到这类结构上的取舍。

## 四、平台

EDA 工具官方推荐开源组合：VS Code + Icarus Verilog + GTKWave + git。

板卡指定紫光同创 Logos-2 PG2L100H，但补了一句"或者资源相当的开发板都可以"。这句补充很关键：我们现在是用 Xilinx Zynq-7020 做的综合和时序分析，100 MHz 时序约束实际跑到 50 MHz 收敛，属于资源相当的范围。不过报告里必须把芯片型号和这个等价性论证写清楚，不能含糊过去，否则那 20 分有风险。

## 五、核心概念，用一段话讲完

FIR 滤波器的本质是滑动加权平均。每来一个采样点，取最近 81 个点，各乘一个预设权重（系数），再加起来，得到一个新数。系数选得好，高频成分互相抵消、低频保留，就成了低通滤波。

为什么要用硬件做？假设采样率 50 MHz，每秒要完成 50M × 81 ≈ 40 亿次乘加。CPU 用软件循环算，就算一个周期一次乘法也要 80 拍才出一个结果；做成 82 个乘法器并行的专用电路，每个时钟周期就能吐一个。

"81 阶"这个词容易混淆——它指的是 81 阶多项式，对应 82 个抽头（系数）。项目里 `NTAP=82` 和文档里说的"81 阶"是同一件事，代码里统一用 82。

## 六、项目现在是什么状态

四个月的迭代之后，骨架已经完整。26 个测试台全部通过，功能覆盖 86/86 个必达点，过程语句行覆盖 99.49%。

具体到赛题的五条硬性要求：

| 要求 | 完成情况 |
|---|---|
| 81 阶可配置 FIR，系数/数据 16bit，吞吐 ≥1 sample/cycle | 82 抽头全并行，7 级加法树 + 5 级流水，实测 1 sample/cycle |
| AXI 互连、仲裁、AHB→AXI、AXI→APB | 5 个主设备接入，527 项检查无死锁 |
| 6 通道 DMA，完成中断 | 6 通道独立配置，含 6 通道并发压力用例 |
| C 驱动软硬协同 | 固件配系数 → 下 DMA → 读结果，337 拍逐位比对 |
| FPGA 综合，≥25MHz（目标 50MHz） | 50 MHz 时序收敛，WNS +0.217 ns |

资源占用（Zynq-7020）：12,782 个 LUT、9,108 个 FF、16 个 BRAM36、85 个 DSP。DSP 占了 39%，这个数字看起来高，其实是"全并行换 100% 吞吐"的代价，也是后面做对称系数优化的出发点。

还剩一件事没做：技术报告。素材其实都在手上——契约文档、验证计划、覆盖率报告、综合时序报告，分散在 `docs/` 各个子目录里，缺的是把它们组织成赛题要求的那四段式。

## 七、仓库结构和文档怎么找

```
RTL/      交付 RTL（含 ARM Cortex-M0 原厂 IP）
TB/       26 个测试台 + 检查器/存储模型等辅助件
sw/       固件：启动代码、主程序、链接脚本、编译脚本
sim/      一键仿真脚本和覆盖率统计
fir/      系数设计与黄金模型
synth/    综合脚本与约束
docs/     团队文档（见下）
```

`docs/` 按用途分了四层，`docs/README.md` 是总索引：

- `契约/` —— 八个接口契约，改之前必须全队确认，是全项目最权威的文件
- `阶段划分/` —— 各阶段分工与交接记录
- `学习资料/` —— 入门材料，从名词到工具用法
- `validation-20261018/` —— 综合、时序、DRC 的原始证据

顶层还有几份独立的：`任务3-地址映射与中断分配.md`（地址表）、`任务4-模块接口信号清单.md`（端口表）、`任务5-FIR定点方案说明书.md`（位宽与结构论证）。

## 八、上手顺序

第一天别急着写代码。先花两小时读 `赛题全景与行动手册.md`（就是本文）建立全局观，再翻 `契约/契约1-接口契约（冻结版）.md` 搞清模块边界，然后跑一遍 `sim\sim.cmd` 看 26 个测试台怎么跑起来的。跑通了，再去读某个模块的 RTL，对照 `任务4` 的端口表看信号。

想改哪个模块之前，先确认它属于哪份契约的管辖范围——契约是冻结的，单方面改动会让别人的测试台一起挂。

## 十、几句实在话

这个项目最消耗时间的不是写 RTL，而是调试。仿真跑不通的时候，先看波形再改代码，比盯着源码想半小时有效得多——我们排查过的一个总线故障，根因是构建产物 `firmware.hex` 过期，字面量池里的一个常量被写坏了，CPU 取到非法地址直接进 HardFault。这种问题靠读代码是看不出来的。

文档要边做边写。报告占 15 分，而且是所有评分项里唯一"现在写就一定有分"的东西，堆到最后两天写的版本，通常既缺数据又缺论证。

还有一句：别怕推倒重来。这个项目的 AHB 桥改过三版，FIR 的累加结构从 81 级串行链换成加法树，每一次重写都让后面的调试轻松一截。
